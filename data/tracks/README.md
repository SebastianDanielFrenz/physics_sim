# data/tracks

## test_ground (M1 -- first test drive)

Generated by `tools/trackgen` (stdlib-only Python, no Blender needed):

```
py -3.13 tools/trackgen/build.py                 # writes everything below
py -3.13 tools/trackgen/validate.py               # structural + physical checks
py -3.13 tools/trackgen/validate.py --determinism  # + rebuild-in-memory byte check
py -3.13 tools/trackgen/render_terrain_preview.py  # out/renders/terrain_heightmap_*.png
```

The world is **two complementary sources**, deliberately never mixed (PLAN.md
section 6 / P11 seam for a later real-world DEM + land-cover module behind
the same interfaces):

1. **Terrain spec** -- `test_ground/terrain.json` (+ `terrain_golden.json`).
   A 100 x 100 km (+-50 km) procedural, deterministic height field plus a
   *per-cell* surface id (one id per 256 m tile, `tiling.tile_size_m`), meant
   to be evaluated by a future C++ tile system in `core/`, not by this
   package. `terrain.json` documents the exact formula (a MurmurHash3-style
   32-bit integer hash, bilinear value noise, fbm octaves, a radial
   "roughness" ramp for occasional steeper hills far from the origin, and the
   flat-zone blending) precisely enough to reimplement bit-for-bit; run
   `tools/trackgen/trackgen/terrain.py` as the Python reference. Height is
   exactly 0 inside a few **flat zones** -- a 3 km-radius disc around the
   origin (holding every feature below except the two long ones) and a flat
   corridor each for the long straight and the airstrip -- blending smoothly
   into the noise outside them, so no meshed feature ever depends on the
   noise function. `terrain_golden.json` is a few hundred `(x, y) -> (z,
   tile_x, tile_y, surface)` samples for the future C++ implementation to
   test against.
2. **Feature meshes** -- `test_ground/test_ground.glb` + collision (below).
   Exact static meshes for every test area PLAN.md's M1 section asks for,
   each sitting on one of the flat zones above: the straight, skidpad, grass
   and dirt patches, a split-mu strip, ramps at 5/10/15/30/50 %, a side
   slope, a small (~1.65 km) circuit, a 10 km top-speed straight (a car needs
   several km to reach top speed and to brake) and a 1500 m + 2x200 m-overrun
   airstrip with a >= 2 km obstacle-free approach each end (P6). Visually
   plain: this is a test ground, not a showcase.

A meshed feature's own footprint always wins locally (its collision surface
applies); the terrain's per-cell surface only fills the open ground around
and between features.

### Frame

World frame: **local east-north-up**, x = east, y = north, z = up, metres --
algebraically identical to a vehicle's own ISO 8855 frame (x forward, y
left, z up, same right-handed x,y,z=up axes), so no basis change is needed
between them: the world is simply oriented so the main spawn's forward (+x)
is due east and its left (+y) is due north. A vehicle's forward/left only
equal east/north when it faces due east (heading 0). Origin (0, 0, 0) is the
main spawn point, at the centre of `terrain.json`'s main flat disc.

The `.glb` itself uses glTF axes (+Y up, +Z forward, +X left), the same
convention as `data/models`: `gltf(x, y, z) = world(y, z, x)`.

### Surface parameters

`data/surfaces/surfaces.json` is the *one* shared table of physical
parameters (`lambda_mu` -- Pacejka-style friction scale relative to dry
asphalt = 1.0, `crr` -- rolling-resistance coefficient, a display name and
the source for each value) for every surface id used by either source
(`grass`, `dirt`, `field` for the open terrain; `asphalt`, `kerb`, `low_mu`
for the meshes). Both `test_ground.json` (`surfaces_file`) and `terrain.json`
(`surface_params_ref`) reference it rather than embedding a copy, so a later
real-world land-cover module can map its own classes onto the same ids/
values. Sources are Wong, *Theory of Ground Vehicles*, or a plausible
published range flagged as such where no direct measurement is cited (PLAN.md
section 8).

### Collision format

Triangle meshes grouped **by physical surface** (not by feature/part), as a
compact binary sidecar (`test_ground_collision.bin`) plus a JSON index
(`test_ground_collision.json`), rather than separate `col_<surface>` nodes in
the `.glb`. Reasoning: the collision consumer is the physics core, not a
renderer -- a raw `float32[]`/`uint32[]` blob per surface loads with no glTF
parser dependency in C++, and grouping by surface (rather than by the dozen
separate visual parts) is exactly the lookup the tyre/contact code needs
(one triangle soup per friction/rolling-resistance id). Keeping it out of the
`.glb` also means Godot's own glTF import never has to filter collision-only
nodes out of the render tree. Format: per surface, `float32[vertex_count*3]`
positions (world ENU frame, *not* glTF-converted) then
`uint32[index_count]` indices local to that surface's own vertex block --
see the file itself for the exact byte layout.

Collision is exact at slopes and ramp edges and has no cracks/T-junctions
because every feature is generated as *one* connected mesh (`ribbon.py`):
vertices along a feature's own length are shared by construction, and where
two different materials meet within one feature (e.g. asphalt/kerb on the
circuit, asphalt/low_mu on the split-mu strip) the boundary vertices are still
the same float coordinates on both sides, just tagged into different
(part, material) groups -- watertight by construction, not by after-the-fact
snapping. `validate.py` checks this (edge-manifoldness per surface, no
degenerate triangles, upward normals, and no two surfaces overlapping at
different heights).

### Visual grid

The 1 m/10 m speed-and-distance grid is **not** a mesh texture (impossible to
tile sensibly over a 100 km world): it is left to a world-space shader in the
Godot adapter (P2). Feature meshes themselves are plainly textured
(procedural asphalt/grass/dirt/kerb/low_mu/marking materials, see
`tools/trackgen/trackgen/textures.py`).

### Checking a model

- `tools/trackgen/validate.py` (above).
- Terrain preview: `tools/trackgen/render_terrain_preview.py` writes a coarse
  grayscale heightmap PNG of the whole world and a zoomed view around the
  origin to `out/renders/` (git-ignored).
- Blender (independent importer + preview render, own script -- does not
  touch `tools/assetgen/blender_check.py`):
  `"S:\programs\Blender 5.2\blender.exe" -b --factory-startup --python-exit-code 1 -P tools/trackgen/blender_preview.py`
  writes `out/renders/track_top.png`, `track_persp.png` and
  `track_ramps.png`.

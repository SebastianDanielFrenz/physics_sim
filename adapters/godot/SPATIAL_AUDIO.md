# Windows spatial audio / Dolby Atmos

The Godot adapter now registers `PsSpatialAudio`, a Windows Spatial Sound output using `ISpatialAudioClient` dynamic objects. The demo attempts this automatically for vehicles with a live engine voice. Each existing intake/exhaust radiating channel is preserved, positioned using its installation's vehicle-frame position, and transformed relative to the current camera (the tracked XRCamera in VR). One-metre calibrated source pressure is used as the input level. The demo uses an artistic 8 m reference distance: full gain inside 8 m, then 8/distance falloff. This keeps the nearby chase/free cameras audible without boosting cockpit audio. PsSpatialAudio defaults to a physical 1 m reference for other callers; set_reference_distance_m controls this presentation mix. Windows performs spatial rendering. Rear speakers follow source direction: a car ahead of the chase camera belongs in front, while exhaust behind the cockpit listener belongs behind.

Select **Dolby Atmos for Headphones** or **Dolby Atmos for home theater** for the Windows default multimedia output device, with the appropriate Dolby Access activation and compatible HDMI equipment for home theater. The same integration also works with Windows Sonic and DTS spatial providers. The game does not change system settings or install/activate Dolby software. A successful stream log says Windows spatial objects are active; this does not certify which provider the user selected.

If the selected device does not support enough dynamic objects, rejects the 48 kHz mono float format, or is lost during playback, the demo uses its existing Godot audio generator. `drive --m1-audio=godot` forces that fallback. After an endpoint change, restart the demo to attempt spatial output on the new default device. The native backend currently follows the Windows default multimedia device, not Godot's custom output-device selection.

Only existing engine voice channels are routed in this pass. Tyre, impact and environmental audio can use additional `PsSpatialAudio` instances with interleaved mono PCM and listener-relative positions; those sound generators are not invented here. The committed `car_hyper` uses a torque-map engine; the pending working-tree engine definition uses a live simulated voice. This backend accepts PCM from either an engine renderer or any other game sound source. Doppler, cabin filtering and reverberation remain game-side work.

The audio worker owns its COM apartment, stream and objects. A bounded 16384-frame queue separates main-thread voice readback from event-driven device rendering; target queued spatial audio is 20 ms (the exclusive PCM diagnostic uses a separate 200 ms queue). No Godot objects or physics state are accessed by the audio thread. Missing samples become silence. Endpoint/stream errors deactivate the backend and allow the demo to resume its single existing voice consumer through Godot.

Validation: build `ps_godot_adapter`; run `--headless --script res://scripts/test_spatial_audio.gd` for invalid-format/channel rejection, supported-device opening, silence feeding, and idempotent shutdown. Run the normal `car_sedan_pipes --m1-autopilot` smoke both with default spatial output and with `--m1-audio=godot`. Perceptual direction and headset/device-specific listening still require manual validation.

References: [Microsoft Spatial Sound](https://learn.microsoft.com/en-us/windows/win32/coreaudio/spatial-sound), [object-rendering API example](https://learn.microsoft.com/en-us/windows/win32/coreaudio/render-spatial-sound-using-spatial-audio-objects).


The demo enables a 0.15-gain diffuse reflection layer on supported back-left/right and top-front/back-left/right static bed channels. It uses decorrelated 31–68 ms filtered delays with feedback, an artistic mix rather than geometry-traced environmental acoustics; the direct object positions are unchanged. Generic PsSpatialAudio callers have reflections disabled by default. Enable the layer before opening the stream using set_reflections_gain.

Run `drive --m1-speaker-test` for a 22-second, eleven-position dynamic-object sweep (front L/C/R, sides L/R, rears L/R and four heights), with no LFE or reflection layer. Each position is announced in the console. Panning may distribute a test position across adjacent speakers according to the Windows renderer. Use `--m1-audio-debug` on a normal drive to log the actual listener name and source coordinates once per second (+Z behind, +Y above). Startup reports the chosen Windows default multimedia device and native bed mask; this is capability evidence, not a measurement of downstream TV/AVR speaker output.
`audio_probe` opens an independent live diagnostic window: drag the source in a top-down plane and adjust height/volume. Tone playback starts muted. The probe uses dynamic objects with reflections disabled and constant gain within its positioning range. Reconnect audio reopens the current Windows default multimedia endpoint.
The probe also has Direct: Surround L and Direct: Surround Back L buttons. They open static AudioObjectType_SideLeft and AudioObjectType_BackLeft streams respectively, bypassing dynamic positional panning, attenuation and reflection processing. Each starts the same diagnostic tone at the current volume. Dragging the position dot or pressing Reconnect returns to dynamic positional mode.
The 7.1 PCM buttons use exclusive WASAPI at 48 kHz/16-bit with WAVEFORMATEXTENSIBLE channel mask 0x63f (FL FR FC LFE BL BR SL SR). Surround L is channel index 6; Surround Back L is index 4. Only the selected channel contains signal. No Atmos encoder, reflection bed or stereo fallback is used. Exclusive playback temporarily takes the device from shared audio apps, and releases it on mute, focus loss or exit. Verify the receiver reports multichannel PCM and disable receiver upmixing during the comparison. An endpoint capability success does not verify downstream TV passthrough.

## Reusing the backend in another Godot game

The committed backend consists of src/spatial_audio.cpp and src/spatial_audio.h, its PsSpatialAudio registration, the adapter CMake source entry, and the Windows ole32 link. It depends on godot-cpp and the Windows SDK; it has no engine/core or VehicleVoice dependency. The calling game supplies 48 kHz interleaved float PCM and one listener-relative position per source channel. Godot coordinates use +X right, +Y up, -Z ahead. Transform each world-space source by the inverse tracked VR camera transform before set_positions.

Instantiate PsSpatialAudio, call open(48000, channel_count), and feed get_frames_needed() frames from the main thread. If open returns false or is_active becomes false, route the source to the game's Godot AudioStreamGenerator fallback. Close it on shutdown. The native API does not create that fallback automatically. set_reference_distance_m controls distance gain and set_reflections_gain enables the optional reflection bed. These classes do not initialize OpenXR; the calling game owns VR setup and supplies the tracked listener.

The reusable backend commit does not include the pending demo camera routing, engine/turbo/audio-bank changes, or diagnostic UI. Its lifecycle check is res://scripts/test_spatial_audio.gd. Successful object-stream activation establishes API/device support; Dolby provider selection and receiver/headset listening require checking the actual playback setup.
